1. PRODUCT UNDERSTANDING BASED ON SUPPLIED REQUIREMENTS
1.1 Executive Product Vision
Zunme AI is conceptualized as an integrated, unified AI productivity workspace tailored for individuals, creators, influencers, entrepreneurs, and modern small businesses. Rather than forcing users to jump between fragmented utilities (e.g., standard conversational LLM interfaces, separate web search engines, standalone copy generators, and disconnected note-taking tools), Zunme AI consolidates the daily creative and research workflow into a single cohesive SaaS platform.

Over time, Zunme AI is envisioned to evolve into a multi-faceted AI ecosystem featuring:

Intelligent conversational assistance.
Web research with verified, live source attribution.
Rapid text and marketing content generation.
A persistent personal content library.
A creator discovery and asset marketplace.
Multi-platform social publishing and scheduling.
Small-business and CRM workflow integration (including potential nErgy CRM alignment).
An integrated advertising and sponsored distribution platform (Zunme Ads).
Creator monetization and transparent revenue-sharing.
1.2 Phase 1 MVP Core Purpose
Phase 1 does not attempt to launch the complete ecosystem at once. Instead, it delivers a rock-solid, high-utility, testable Minimum Viable Product (MVP) that solves the core problem: allowing an authenticated user to research live topics, converse with an AI assistant, generate production-ready text content, and store their outputs reliably in a personal library.

Every functional capability in Phase 1 (Chat, Web Search, Content Studio, and My Library) will be backed by genuine API providers and server-side persistence—never placeholder screens or mocked client-side stubs.

2.2 Architectural Assumptions
Tech Stack Recommendation: Since the repository is currently empty, we propose a standardized, type-safe full-stack TypeScript architecture:
Frontend: React 18+ with Vite, TypeScript, React Router v6, TailwindCSS + custom tokens matching the specified palette, Lucide React icons.
Backend: Node.js with Express (or Fastify) and TypeScript, Zod schema validation, Prisma ORM with PostgreSQL (or SQLite for local dev if cloud DB is pending).
Authentication: Stateless JSON Web Tokens (Access Token in memory/header, Refresh Token in httpOnly secure cookie) with Argon2/bcrypt password hashing.
Search Provider: Integration with a specialized search API such as Tavily Search API or Serper.dev, which return structured, verified URLs, snippets, and page titles rather than raw HTML scraping.
AI Provider: Integration with OpenAI API (gpt-4o-mini or gpt-4o) or Anthropic Claude 3.5 Sonnet via server-side SDKs.
2.3 Open Questions & Unanswered Client Decisions
#	Question / Decision Area	Context & Impact	Proposed Default (If Not Specified)
Q1	Streaming vs. Request-Response	Does the MVP AI Chat require real-time token streaming via Server-Sent Events (SSE), or is standard JSON response acceptable?	Recommendation: Implement SSE streaming for Chat and Web Search summaries for modern SaaS responsiveness.
Q2	Live Email Delivery (SMTP/SaaS)	Is an email delivery provider (Resend, SendGrid, AWS SES) provisioned for MVP signup verification and password reset?	Recommendation: For local MVP testing, log password reset tokens to server console; integrate Resend/SendGrid when credentials are provided.
Q3	Search & AI Provider Provisioning	Which specific commercial AI provider (OpenAI, Anthropic, Gemini) and Web Search API (Tavily, Serper, Brave) will be funded?	Recommendation: OpenAI (gpt-4o-mini for cost efficiency) and Tavily API (built specifically for AI agent search grounding).
Q4	Usage Quotas & Rate Limits	Should the MVP enforce per-user daily token or search caps to prevent API billing spikes?	Recommendation: Set soft rate limits (e.g., 30 chats/hour, 20 searches/hour per user) enforced via Redis/in-memory rate limiter.
Q5	Library Item Editing	Should users be able to edit the content of saved items in My Library, or is the MVP strictly View, Copy, Filter, and Delete?	Recommendation: View, Copy, and Delete in Phase 1; inline rich-text editing deferred to Phase 1.1.
Q6	Minimal Admin Permissions	Does admin need user impersonation or destructive deletion, or strictly user listing, status toggling (active/suspended), and aggregate counts?	Recommendation: Strictly read-only statistics and user status toggling (active / suspended).

Detailed Flow Descriptions & Edge Cases
Flow 1: New User Onboarding
Entry: Visitor arrives at / (Landing Page).
Action: Clicks [Start Creating Free] or [Get Started].
Validation: On /register, system verifies valid email format, full name presence, and password complexity (minimum 8 characters).
Authentication: Backend hashes password, provisions user record, generates JWT access and refresh credentials.
Destination: Redirected into /app/chat with an initialized welcoming conversation and starter prompt pills.
Failure/Retry: If email already exists, form displays accessible alert: "An account with this email already exists. Sign in instead."
Flow 2: AI Conversation Lifecycle
Submission: User enters prompt into ChatInputBar and submits.
Optimistic Rendering: User message appears instantly in chat log; input clears; typing indicator activates.
Backend Processing: Backend validates session, attaches system prompt, checks rate limits, and sends payload to LLM provider.
Response Delivery: Complete AI response is rendered with markdown formatting and syntax highlighting.
Persistence: Both user and assistant messages are stored in database linked to conversationId.
Failure/Retry: If LLM provider times out or responds with an error, the assistant bubble shows an error notice with an active [Retry] button.
Flow 3: Web Research Lifecycle
Query: User enters topic (e.g., "Latest developments in quantum computing 2026") on /app/search.
Search Execution: Backend invokes web search provider, obtaining top 3–5 high-relevance URLs, titles, and authoritative text snippets.
Grounded Synthesis: Backend sends retrieved snippets to LLM with grounding instructions to formulate an executive summary without fabricating external facts.
Attribution Display: Frontend displays the AI overview followed by distinct, clickable SourceCard items with verified URLs.
Save Action: Clicking [Save Research] packages the summary and source metadata into a persistent SavedItem record.
Flow 4: Content Studio Creation
Configuration: User navigates to /app/studio, picks category (Marketing & Social Copy), format (Ad Copy), target tone (Persuasive), length (Short), and inputs product context.
Generation: Backend constructs structured system prompt and queries LLM.
Review & Output: Generated copy renders in StudioOutputPane with word count and copy button.
Storage: User clicks [Save to Library]; item is stored under category MARKETING.
Flow 5: Saved Content Management
Discovery: User navigates to /app/library.
Filtering: User clicks Research filter pill; library instantaneously filters to research briefs.
Inspection: Clicking [View] opens ViewItemModal with full formatted text, citations, and creation date.
Deletion: Clicking [Delete] triggers a confirmation modal to avoid data loss. Upon confirmation, item is purged from database.

Relational Schema Definitions (Prisma / SQL Equivalent)
prisma
enum Role {
  USER
  ADMIN
}
enum ContentType {
  TEXT
  MARKETING
  RESEARCH
}
model User {
  id            String         @id @default(uuid())
  email         String         @unique
  passwordHash  String
  fullName      String
  role          Role           @default(USER)
  isActive      Boolean        @default(true)
  conversations Conversation[]
  savedItems    SavedItem[]
  createdAt     DateTime       @default(now())
  updatedAt     DateTime       @updatedAt
  @@index([email])
}
model Conversation {
  id        String    @id @default(uuid())
  userId    String
  user      User      @relation(fields: [userId], references: [id], onDelete: Cascade)
  title     String    @default("New Conversation")
  messages  Message[]
  createdAt DateTime  @default(now())
  updatedAt DateTime  @updatedAt
  @@index([userId])
}
model Message {
  id             String       @id @default(uuid())
  conversationId String
  conversation   Conversation @relation(fields: [conversationId], references: [id], onDelete: Cascade)
  role           String       // "user" | "assistant" | "system"
  content        String       @db.Text
  createdAt      DateTime     @default(now())
  @@index([conversationId])
}
model SavedItem {
  id             String      @id @default(uuid())
  userId         String
  user           User        @relation(fields: [userId], references: [id], onDelete: Cascade)
  title          String
  contentType    ContentType @default(TEXT)
  content        String      @db.Text
  sourceMetadata Json?       // Stores [{ title, url, snippet }] for RESEARCH items
  createdAt      DateTime    @default(now())
  updatedAt      DateTime    @updatedAt
  @@index([userId, contentType])
}

11. RISKS AND DECISIONS REQUIRING CLIENT CONFIRMATION
Key Architectural Risks & Mitigation Strategies
Search & AI Provider Outages / Latency:
Risk: Third-party AI or Web Search API spikes to 8+ seconds latency or encounters rate limit errors.
Mitigation: Implement server-side request timeouts (15s maximum), clear UI loading progress states, and actionable error alerts with a single-click retry mechanism.
Credential & API Key Security:
Risk: AI provider API keys accidentally leaked into client-side bundles.
Mitigation: Strict architecture isolation. Client communicates only with the Zunme backend API. All third-party provider keys reside exclusively in backend environment variables (.env).
Database Authorization Leaks:
Risk: Malicious user accesses or deletes another user's saved research or chat messages by guessing UUIDs.
Mitigation: Server-side ownership guards on every single entity query (e.g., WHERE id = :id AND userId = :currentUserId).
